# ADR-001 分层与仓储查询封装规范

- 状态：已采纳
- 日期：2026-11-02
- 决策人：Mimo（用户）& 架构协作者
- 关联项目：oceanho-stack / services/iam-server

## 背景

在自研一套多端（产品官网 / Console / 手机App / CLI）共用的 B2B SaaS 身份与多租户底座（IAM）时，需要确立一套统一、可扩展、职责边界清晰的分层规范，并且优先复用成熟组件（Gin、GORM、Casbin、Redis），自研只覆盖领域模型与业务边界部分。

核心诉求：
1. 后端 Go，前端以 Vue3 + Vben Admin 起步（后续可单独扩展 React，后端为标准 REST/OpenAPI 不受影响）。
2. 数据库操作使用 GORM v2，不强制绑定数据库特性。
3. 全链路统一请求/响应结构，多端共用。
4. 查询条件收敛、通用工具封装，杜绝在 service/handler 中散写 `Where`。
5. 分层清晰，方便长期扩展（新增业务模块、新增端）。

## 决策

### 1. 总体分层（实用派仓储模式，非学院派 DDD）

```
internal
├── domain          # 领域模型，纯定义，无 gorm / gin 依赖
├── dto             # API 入参/出参 DTO，供 OpenAPI / 多端使用
├── repository      # 数据访问层：BaseQuery / TenantScopedQuery + 各实体 Repo
├── service         # 业务层：接收 AuthPrincipal，做业务/权限/缓存/多 repo 组装
├── handler
│   ├── http        # gin handler：绑定 dto → 转 query → 调 service → dto 映射 → 返回 xresp
│   └── middleware  # trace / auth / tenant / audit / ratelimit / cors
└── policy          # Casbin 授权逻辑

pkg                 # 项目内通用工具，与业务解耦：xresp / xpage / xctx / xtrace / xvalidator / xid ...
```

职责边界（硬性约束）：
- **domain 绝不导入 gorm、gin、casbin**。
- **repo 只提供 List/Get/Create/Update/Delete**，不含业务规则；`*gorm.DB` 句柄不对外暴露。
- **service 持有 repo**，承载业务校验、权限判定、缓存、事件、事务编排。
- **handler 极薄**，只做参数粘合与 DTO 映射，不写业务逻辑、不写查询条件。
- 所有数据库操作只发生在 repository；service/handler 禁止直接调用 `db.Where`。

### 2. 仓储查询封装（对标 my-repo-syncer 范式）

每个实体一个 `xxxQuery` 条件构造器 + 一个 `xxxRepo`：

- 查询条件全部收拢在 `*Query` 结构体，链式方法暴露。
- 链式方法返回**副本**，不修改原对象（避免共享/复用/并发时条件被意外篡改）：

```go
func (q *TenantQuery) WhereNameLike(v string) *TenantQuery {
    cp := *q
    cp.NameLike = v
    return &cp
}
```

- 基础 Query 拆两层，避免全局资源被误加租户过滤：
  - `BasePageQuery`：分页、排序、预加载，所有 repo 通用。
  - `TenantScopedQuery`：内嵌 BasePageQuery，额外提供 tenantID 租户过滤，仅租户隔离资源使用。
- repo 示例：

```go
func (r *TenantRepo) List(ctx context.Context, q *TenantQuery) ([]*domain.Tenant, int64, error) {
    var list []*domain.Tenant
    var total int64
    tx := r.DB().WithContext(ctx).Model(&domain.Tenant{})
    if err := q.Apply(tx).Count(&total).Error; err != nil {
        return nil, 0, err
    }
    if err := q.Apply(tx).Find(&list).Error; err != nil {
        return nil, 0, err
    }
    return list, total, nil
}
```

### 3. 领域模型（多租户 IAM 底座）

核心关系：User 全局账号，可加入多个租户；租户内有树形团队。

```
tenants           租户主表（一等公民，有自己的属性与生命周期）
users             全局用户
tenant_members    User <-> Tenant 多对多，绑定租户级角色
teams             租户内团队（树形，parent_id）
team_members      User <-> Team 多对多，绑定团队级角色
roles             角色（tenant / team 两级 scope）
permissions       权限原子（resource:action）
invitations       邀请（支持未注册用户）
oauth_clients     OIDC 客户端（每个端一个 client：官网/console/app/cli）
api_keys          CLI / 自动化 / 服务间调用
```

### 4. 统一请求 / 响应协议（多端共用）

- HTTP 200 统一承载业务结果，业务对错看 `code`；HTTP 401/403/404/500 仅用于网关与鉴权层。
- 响应体：

```go
type Resp[T any] struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
    Data    T      `json:"data,omitempty"`
    TraceID string `json:"trace_id"`
}
```

- 分页：

```go
type PageReq struct {
    Page     int    `json:"page" form:"page"`
    PageSize int    `json:"page_size" form:"page_size"`
    Sort     string `json:"sort,omitempty" form:"sort"`
    Order    string `json:"order,omitempty" form:"order"`
}
type PageResp[T any] struct {
    List     []T   `json:"list"`
    Total    int64 `json:"total"`
    Page     int   `json:"page"`
    PageSize int   `json:"page_size"`
}
```

- Header 约定：`Authorization: Bearer <token>`、`X-Tenant-Id`（当前选中租户，可空）、`X-Client-Type`（console/website/app/cli）、`X-Trace-Id`（前端可传，后端兜底生成）。
- URI 版本：`/api/v1/...`。

### 5. 上下文传递

- `ctx context.Context` 只承载链路追踪、超时、取消信号。
- 业务身份信息（user_id / tenant_id / client_type）从 ctx 提取后封装为 `AuthPrincipal` 结构体传给 service；service 不直接依赖 gin 上下文工具包，便于未来拆 RPC 服务。

## 后果

优点：
- 查询条件集中、可复用、便于加白名单，杜绝 SQL 散落与注入风险。
- domain 与传输解耦，多端 / OpenAPI 稳定。
- 分层清晰，新增业务模块与新增端成本低。

代价 / 取舍：
- 比传统 handler 直写 SQL 多一层样板代码。
- DTO 引入小幅映射成本。
- Query 放在 repository 包（而非 domain 的 Specification），属实用取舍，代价可控。
