# ADR-005 开发前先调研开源成熟方案

- 状态：已采纳
- 日期：2026-11-02
- 决策人：Mimo（用户）& 架构协作者
- 关联项目：oceanho-stack / go-libs / iam-core / iam-server

## 背景

推进 IAM 时，用户明确要求：**在设计/开发任何能力之前，先查阅市面（GitHub 等）成熟的开源解决方案，而不是盲目自研**：

> "在做一件功能之前，我们需要去查阅市面上 GitHub 上面开源的一些成熟的解决方案，而不是首先就盲目的去自己思考，然后这样子去做。"

这延续了 ADR-002"先抽通用工具、不造轮子"的哲学，但更进一步：**不是只在"工具"层面复用，而是在"任何能力"层面都先问一句"现成成熟方案有没有"**。

## 决策

### 1. 强制流程：任何能力开发前，先调研

设计 / 开发一个能力（认证、授权、多租户、文件、缓存、消息……）之前，**必须先做一轮开源调研**，回答三个问题：

1. **有没有成熟方案？**（语言匹配、star 量级、许可证、维护活跃度）
2. **能否复用 / 封装，而不是重写？**
3. **如果自研，差异化的理由是什么？**（现成没有 / 形态不匹配 / 要深度定制）

只有调研结论明确指向"自研"，才进入设计。禁止"先盲目自研、后知后觉发现有人做过"。

### 2. "成熟"判定标准

调研时用以下标准过滤，**避免误用"几个 star 的玩具项目"**：

| 维度 | 判定 |
|---|---|
| star 量级 | 优先 **≥ 1k star**；核心基建（协议库/框架）≥ 5k 更有保障 |
| 许可证 | 优先 **Apache-2.0 / MIT / BSD**（宽松，可商用可内嵌）；AGPL 慎用（传染性） |
| 维护活跃度 | 近 3–6 个月有提交 / 发布，issue 有响应，非弃坑 |
| 生产验证 | 有明确"生产使用中"背书（被知名项目依赖 / 有托管服务 / 有认证如 OpenID Certified） |

### 3. 决策树：复用 / 封装 / 自研

```
能力要开发？
└─ 调研（按"成熟"标准筛出候选）
   ├─ 有成熟库且形态匹配 → 复用（直接 import / 封装薄层）
   ├─ 有成熟库但形态不符 → 评估：封装适配 / 拆分 / 或自研
   └─ 无成熟方案 / 形态本质不匹配 → 自研（记录理由）
```

分层倾向：
- **协议层**（OAuth2 / OIDC / JWT / 密钥轮换）：成熟且高风险，**复用优先**（如 Ory Fosite、golang-jwt），别重写协议细节。
- **授权层**（RBAC / ABAC 引擎）：复用成熟引擎（Casbin / Ory Keto）。
- **领域层**（多租户隔离 / 身份领域建模）：现成开源多为"独立服务"形态，若需"库形态嵌入"，**可自研**（这正是 iam-core 的定位）。

## 本次调研结论（IAM，2026-11）

对开源 IAM / OAuth Provider 做了调研，结论（详见 `docs/调研/开源IAM与OAuth对比.md` 或会话记录）：

1. **现成开源 IAM（Keycloak / ZITADEL / Casdoor / Logto / Authentik）全是"独立服务"**，没有"可被 SDK 嵌入的多租户库"，与 iam-core"库+壳双形态、不共享各自嵌入"定位不匹配。
2. 因此：**身份领域 + 多租户 + 业务权限自研**（现成没有通用库）；**认证协议层复用**（Ory Fosite + golang-jwt，含 kid/JWKS 轮换）。
3. 授权层复用 **Casbin**（已定），可评估 Ory Keto。

## 后果

优点：
- 避免重复造轮子（尤其协议/安全这类高难度、易踩坑的能力）。
- 快速站在成熟方案肩膀上，减少实现量与 bug。

代价 / 取舍：
- 调研本身有成本（每次开发前要查一轮）。
- 复用成熟库引入外部依赖，需评估许可证与维护风险。
- "调研"不等于"照搬"，仍需结合本项目边界取舍（如 ADR-002 的 lib 拆分标准、ADR-004 的数据库无关约束）。
